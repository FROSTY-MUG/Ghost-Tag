# Ghost-Tag Canonical Binary Envelope Specification

This document defines the binary layout of the Ghost-Tag ciphertext envelope stored on NFC tags.

---

## 1. Binary Envelope Layout

All multi-byte integer fields are encoded strictly in **Little-Endian (LE)** byte order.

```
Offset (Bytes)   Field Name          Size (Bytes)   Description
--------------------------------------------------------------------------------------------------
00 .. 03         MAGIC               4 bytes        ASCII "GTAG" (0x47, 0x54, 0x41, 0x47)
04               FORMAT_VERSION      1 byte         0x01 (Version 1)
05               PURPOSE             1 byte         Payload purpose enum (0x01 - 0xFF)
06 .. 21         KEY_ID              16 bytes       128-bit unique Data Encryption Key ID
22 .. 33         NONCE               12 bytes       96-bit AES-256-GCM Initialization Vector
34 .. 37         CIPHERTEXT_LENGTH   4 bytes        uint32 Little-Endian payload length (N)
38 .. (38+N-1)   CIPHERTEXT          N bytes        AES-256-GCM encrypted payload
(38+N) .. (53+N) GCM_TAG             16 bytes       128-bit AES-GCM authentication tag
--------------------------------------------------------------------------------------------------
Total Fixed Overhead: 54 bytes
Total Envelope Length: N + 54 bytes
```

---

## 2. Field Definitions

### `MAGIC` (4 Bytes)
Fixed ASCII character sequence `GTAG` (`0x47`, `0x54`, `0x41`, `0x47`). Envelopes failing magic byte validation are rejected immediately without parsing.

### `FORMAT_VERSION` (1 Byte)
Specifies schema version. Current canonical version is `0x01`. Unknown or future versions trigger `UNSUPPORTED_VERSION`.

### `PURPOSE` (1 Byte)
Categorical classification of the payload:
- `0x01`: `NOTE` (Freeform plaintext memo or recovery fragment)
- `0x02`: `CREDENTIAL` (Authentication token, password, or API key)
- `0x03`: `CONFIG` (Server connection string, Wi-Fi profile, or device settings)
- `0x04`: `RECOVERY_POINTER` (Metadata pointing to offline recovery shards)
- `0x05`: `ASSET_ID` (Physical or digital asset identifier)
- `0xFF`: `CUSTOM` (Application-specific custom binary payload)

### `KEY_ID` (16 Bytes)
A 128-bit random identifier generated via CSPRNG. It allows the recipient or owner to look up the matching wrapped DEK in their local vault without attempting decryption.

### `NONCE` (12 Bytes)
A 96-bit random vector generated fresh for every write operation via CSPRNG. Nonces must never be reused across encryptions with the same key.

### `CIPHERTEXT_LENGTH` (4 Bytes)
Unsigned 32-bit integer in **Little-Endian** format indicating the exact length $N$ of the ciphertext payload in bytes.

### `CIPHERTEXT` ($N$ Bytes)
The encrypted payload bytes generated by AES-256-GCM.

### `GCM_TAG` (16 Bytes)
The 128-bit Galois/Counter Mode authentication tag protecting both the ciphertext and the 26-byte AAD header.

---

## 3. NDEF MIME Record Encapsulation

Ghost-Tag envelopes are written directly to NFC tags as a single raw NDEF MIME Media record:
- **TNF (Type Name Format)**: `0x02` (`TNF_MIME_MEDIA`)
- **MIME Type**: `application/vnd.ghost.secure`
- **Record ID**: Empty
- **Payload**: Raw binary envelope bytes (no Base64, JSON, or hex bloat)

---

## 4. Overhead & Usable Space Calculation

$$\text{Envelope Overhead} = \text{Header (38 bytes)} + \text{GCM Tag (16 bytes)} = 54\text{ bytes}$$

$$\text{Usable Payload Space} = \text{Tag User Capacity} - \text{NDEF TLV Overhead (7B)} - \text{MIME Framing (31B)} - 54\text{B}$$

Example on NTAG215 (504 bytes user memory):
$$\text{Usable Space} = 504 - 7 - 31 - 54 = 412\text{ bytes of plaintext}$$
Any write exceeding available space is rejected with `PAYLOAD_TOO_LARGE` prior to RF transmission.
